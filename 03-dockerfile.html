Cheatsheet 03

Dockerfile

El Dockerfile es la receta para construir tu propia imagen: un archivo de texto llamado exactamente Dockerfile (sin extensión), en la carpeta de tu proyecto, con instrucciones que Docker ejecuta de arriba hacia abajo cuando corrés docker build.

Términos de esta página

Instrucción
Cada línea que empieza con una palabra en mayúsculas (FROM, COPY, RUN…). Es un paso de la receta.
Imagen base
La imagen de la que partís con FROM, por ejemplo node:18: ya trae un Linux con Node instalado, así no empezás de cero.
Capa (layer)
El resultado guardado de cada instrucción. Una imagen es una pila de capas; si una capa no cambió, Docker la reutiliza.
Caché
Las capas guardadas de builds anteriores. Gracias a la caché, un rebuild solo rehace los pasos desde el primero que cambió.
Build context
La carpeta que le pasás a docker build (el . del final). COPY solo puede leer archivos de ahí adentro.
Dependencias
Las librerías externas que usa tu app (en Node, lo que figura en package.json y se instala en node_modules).
Producción / desarrollo
Producción: la versión que usan los usuarios reales, optimizada y estable. Desarrollo: tu entorno de trabajo, donde importa ver los cambios rápido.
Multi-stage
Un Dockerfile con varias etapas (FROM repetido): una para compilar y otra, más liviana, para ejecutar.
Exec form
Escribir CMD o ENTRYPOINT como lista JSON: ["node", "app.js"]. Es la forma recomendada.
.dockerignore
Un archivo que lista lo que no debe entrar al build context (como .gitignore, pero para Docker).
1

Instrucciones

Van en MAYÚSCULAS y se ejecutan de arriba hacia abajo.

Referencia rápida

InstrucciónQué haceEjemplo
FROMImagen base. Siempre la primera. AS nombre define una etapa.FROM node:18
WORKDIRCarpeta de trabajo dentro del contenedor. La crea si no existe (reemplaza a RUN mkdir -p + cd).WORKDIR /home/app
COPYCopia [ORIGEN-PC] → [DESTINO-CONTENEDOR]. El origen es relativo al build context.COPY . /home/app
ADDComo COPY pero además descomprime .tar y acepta URLs. Preferí COPY.ADD app.tar.gz /opt/
RUNEjecuta un comando al construir la imagen (instalar cosas).RUN npm i -g nodemon
ENVVariable de entorno disponible en build y en ejecución.ENV NODE_ENV=production
ARGVariable solo durante el build (--build-arg).ARG VERSION=1.0
EXPOSEDocumenta el puerto de la app. No publica nada (eso es -p).EXPOSE 3000
CMDComando por defecto al iniciar el contenedor. Solo vale el último.CMD ["node", "app.js"]
ENTRYPOINTEjecutable fijo del contenedor; CMD/args se le agregan.ENTRYPOINT ["dotnet", "Api.dll"]
USERUsuario con el que corre (evitar root en producción).USER node
i

RUN vs CMD: RUN se ejecuta una vez al construir la imagen. CMD se ejecuta cada vez que arranca un contenedor.

2

Node.js — imagen de producción

El código queda copiado dentro de la imagen.

Versión básica

Dockerfile mínimo

Dockerfilefunciona ✓
# imagen a utilizar
FROM node:latest

# directorio en el contenedor donde va el código
RUN mkdir -p /home/app

# [ORIGEN-PC] [DESTINO-CONTAINER]
COPY . /home/app

# puerto de la app (informativo)
EXPOSE 3000

# comando + argumentos
CMD ["node", "/home/app/app.js"]
!

No instala dependencias: funciona porque copia tu node_modules local. Si tuvieras dependencias nativas (bcrypt, sharp…) compiladas en Windows, fallarían en Linux.

✕

Error común: COPY E/Development/mi-proyecto /home/app no funciona. COPY no acepta rutas absolutas de tu PC, solo rutas dentro del build context → COPY . /home/app.

Versión mejorada

Dockerfile recomendado

Dockerfileusa caché + reproducible
# versión fija: latest puede cambiar y romper el build
FROM node:18

# crea la carpeta y se para en ella
WORKDIR /home/app

# 1º solo las dependencias (capa cacheable)
COPY package*.json ./
RUN npm ci --omit=dev

# 2º el resto del código
COPY . .

EXPOSE 3000

CMD ["node", "app.js"]
  • WORKDIR reemplaza RUN mkdir -p y permite rutas relativas
  • Si solo cambiás código, npm ci no se vuelve a ejecutar (ver caché)
  • Acompañalo con un .dockerignore que excluya node_modules
3

Node.js — imagen de desarrollo

No copia el código: lo recibe por un volumen (bind mount) desde compose y nodemon recarga al guardar.

Con la imagen de producción, cada cambio de código obliga a reconstruir la imagen (el código quedó copiado adentro). Para desarrollar eso es lento. La imagen de desarrollo no copia el código: en su lugar, Docker Compose monta tu carpeta dentro del contenedor (bind mount), así el contenedor ve tus archivos en vivo.

nodemon es una herramienta de Node que reinicia la app automáticamente cada vez que un archivo cambia. Combinados: guardás en el editor y la app se reinicia sola, sin rebuild.

Dockerfile.dev

Dockerfile.dev
FROM node:latest

# nodemon global para recargar al guardar
RUN npm i -g nodemon
RUN mkdir -p /home/app

WORKDIR /home/app

EXPOSE 3000

# -L = legacy watch (polling)
CMD ["nodemon", "-L", "app.js"]

Por qué así

  • Sin COPY: el código entra por volumes: - .:/home/app en docker-compose-dev.yml
  • Editás en tu PC → el archivo cambia dentro del contenedor → nodemon reinicia
  • No hace falta rebuild por cada cambio de código (solo si cambia el Dockerfile o dependencias globales)
  • -L es necesario en Windows/WSL: los eventos de cambio de archivo no cruzan el bind mount, así que nodemon tiene que consultar (polling)
  • RUN mkdir -p sobra: WORKDIR ya crea la carpeta
✓

Levantalo con docker compose -f docker-compose-dev.yml up.

4

Capas y caché

Si una capa cambia, se reconstruyen esa y todas las de abajo. Lo que cambia poco va arriba.

Cada instrucción del Dockerfile produce una capa, y Docker las guarda. En el próximo docker build, recorre las instrucciones en orden: mientras la instrucción y los archivos que usa sean iguales, reutiliza la capa guardada (dice CACHED). En cuanto una cambia, rehace esa y todas las siguientes.

Por eso conviene copiar primero package.json e instalar dependencias, y recién después copiar el resto del código: el código cambia todo el tiempo, pero las dependencias casi nunca, y la instalación (lo más lento) queda en caché.

Multi-stage build (ASP.NET Core / .NET 10)

Una etapa con el SDK para compilar, otra solo con el runtime para ejecutar. La imagen final es mucho más liviana.

Algunos lenguajes (C#, Java, Go) necesitan compilarse: transformar el código fuente en un programa ejecutable. Para compilar hace falta el SDK (el kit de desarrollo completo, pesado); para ejecutar alcanza con el runtime (solo lo necesario para correr el programa, mucho más chico).

Un Dockerfile multi-stage usa los dos: una primera etapa con el SDK compila, y una segunda etapa con el runtime copia solo el resultado. La imagen final contiene únicamente la segunda etapa: más liviana y sin herramientas de compilación.

Dockerfile

src/<Proyecto>.HttpApi.Host/Dockerfile
# ---------- Etapa 1: compilar ----------
FROM mcr.microsoft.com/dotnet/sdk:10.0 AS build
WORKDIR /src

# toda la solución: Host depende de Domain, Application…
COPY . .

RUN dotnet restore "src/<Proyecto>.HttpApi.Host/<Proyecto>.HttpApi.Host.csproj"
RUN dotnet publish "src/<Proyecto>.HttpApi.Host/<Proyecto>.HttpApi.Host.csproj" \
    -c Release -o /app/publish

# ---------- Etapa 2: ejecutar ----------
FROM mcr.microsoft.com/dotnet/aspnet:10.0 AS runtime
WORKDIR /app
COPY --from=build /app/publish .

EXPOSE 8080
ENTRYPOINT ["dotnet", "<Proyecto>.HttpApi.Host.dll"]

Paso a paso

  1. Etapa build con la imagen del SDK de .NET 10.
  2. WORKDIR /src: nos paramos en una carpeta nueva del contenedor.
  3. COPY . . copia todo el build context (la carpeta aspnet-core completa, así se definió en compose) porque HttpApi.Host necesita los otros proyectos para compilar.
  4. restore + publish. El resultado va a /app/publish — ruta absoluta, no relativa a /src.
  5. Etapa runtime: solo lo necesario para ejecutar.
  6. WORKDIR /app.
  7. COPY --from=build trae lo publicado desde la etapa anterior.
  8. EXPOSE 8080 (informativo; en .NET 8+ el puerto por defecto es 8080).
  9. ENTRYPOINT ejecuta la DLL compilada.
!

El restore separado no aprovecha la caché tal como está. Para que sirva, copiá primero solo los .csproj, hacé restore y recién después COPY . . (mismo truco que package.json en Node). publish igual hace restore si hace falta.

6

CMD vs ENTRYPOINT · forma exec vs shell

Cómo arranca el proceso principal.

CMD

Comando por defecto. Se reemplaza si pasás algo después de la imagen.

CMD ["node", "app.js"]
docker run miapp:1 node otro.js   # reemplaza el CMD

ENTRYPOINT

Ejecutable fijo. Lo que pases (o el CMD) se agrega como argumentos.

ENTRYPOINT ["dotnet", "Api.dll"]
docker run api:1 --urls http://+:5000   # dotnet Api.dll --urls ...

Exec form vs shell form

Usá la forma JSON (exec): el proceso recibe las señales y docker stop lo cierra limpio.

# ✓ exec form
CMD ["node", "app.js"]
# ✕ shell form (corre dentro de /bin/sh -c)
CMD node app.js

8

Construir la imagen

Desde la carpeta donde está el Dockerfile.

Comandos de build

docker build -t miapp:1 .
Construye la imagen con el Dockerfile de la carpeta actual y la llama miapp, versión 1. El . final es el contexto: los archivos que el Dockerfile puede copiar con COPY (menos los que excluye .dockerignore).
docker build -t miapp:dev -f Dockerfile.dev .
-f elige otro Dockerfile, por ejemplo uno para desarrollo con nodemon. El contexto sigue siendo la carpeta actual, así que los COPY se resuelven igual.
docker build --no-cache -t miapp:1 .
Ejecuta todos los pasos de nuevo, sin reutilizar capas guardadas (ver “Capas y caché” arriba). Usalo si sospechás que algo quedó viejo en la caché; el build tarda más.
docker build --target build -t api:build .
En un Dockerfile multi-stage (con varias etapas FROM … AS nombre), construye solo hasta la etapa indicada y se detiene ahí. Sirve para correr los tests o revisar qué produce la etapa de compilación.
docker build --build-arg VERSION=2.0 -t miapp:2 .
Le pasa un valor a una instrucción ARG VERSION del Dockerfile, que existe solo mientras se construye la imagen (no queda como variable de entorno al correr el contenedor). No lo uses para contraseñas: queda registrado en la imagen.
docker build -t api:1 -f src/Api/Dockerfile .
El Dockerfile está en una subcarpeta, pero el contexto es la raíz (.), porque necesita copiar archivos de varias carpetas del proyecto (en .NET, la solución y otros proyectos). Las rutas de los COPY se escriben desde la raíz.
