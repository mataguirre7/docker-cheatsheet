Cheatsheet 04

Docker Compose

Cuando una app necesita varios contenedores (por ejemplo la API y su base de datos), levantarlos a mano con docker run es largo y fácil de equivocar. Docker Compose describe todos los contenedores del proyecto en un solo archivo, y los levanta (o los baja) con un comando.

Términos de esta página

YAML
Un formato de texto para configuración. Usa sangría con espacios para indicar qué está dentro de qué, clave: valor para datos y - para listas.
docker-compose.yml
El archivo de Compose. Por defecto, docker compose busca ese nombre en la carpeta actual.
Servicio
Cada contenedor definido en el archivo (por ejemplo chanchito y monguito). Su nombre funciona además como dirección dentro de la red.
Proyecto
El conjunto de servicios de un archivo Compose. Toma el nombre de la carpeta y se usa como prefijo de contenedores, red y volúmenes.
Red por defecto
Compose crea una red para el proyecto y conecta ahí todos los servicios, así se encuentran por nombre sin configurar nada.
Volumen nombrado
Almacenamiento administrado por Docker que sobrevive a los contenedores; se declara al final del archivo, en volumes:.
Bind mount
Montar una carpeta de tu PC dentro del contenedor (.:/home/app). Se usa para desarrollo.
Variable de entorno
Un valor de configuración (NOMBRE=valor) que el contenedor lee al arrancar.
.env
Un archivo con variables (una por línea) que Compose lee solo. Se usa para no escribir contraseñas en el YAML; no se sube a git.
Healthcheck
Un chequeo periódico que dice si un servicio está realmente listo (por ejemplo, si la base de datos ya acepta conexiones).
1

Qué pasa con docker compose up

Del YAML a contenedores, red y volumen.

Al correr docker compose up en la carpeta del archivo, Compose lee el YAML y hace por vos lo que harías con varios comandos: construye las imágenes que tengan build, descarga las que tengan image, crea una red para el proyecto, crea los volúmenes y arranca cada servicio con sus puertos y variables. docker compose down hace lo inverso: detiene y borra contenedores y red (los volúmenes quedan, salvo que agregues -v).

i

El prefijo mi-proyecto sale del nombre de la carpeta (nombre del proyecto). Cambialo con -p <nombre> o con name: arriba del YAML.

2

Comandos de compose

Se ejecutan en la carpeta del docker-compose.yml.

Levantar y bajar

docker compose up
Lee el docker-compose.yml y levanta todo el proyecto: construye las imágenes que tengan build: (solo si no existen todavía), crea la red, los volúmenes y los contenedores, y los arranca. La terminal queda mostrando los logs de todos los servicios mezclados; Ctrl+C los detiene.
docker compose up -d
Lo mismo, en segundo plano (detached): te devuelve la terminal y los servicios siguen corriendo. Los logs se ven con docker compose logs.
docker compose up --build
Fuerza el rebuild de las imágenes (cuando cambiaste el Dockerfile o el código en prod).
docker compose down
Detiene y borra los contenedores y la red que creó el proyecto. Los volúmenes (y por lo tanto los datos de la base) se conservan, así que el próximo up los encuentra. Las imágenes tampoco se borran.
docker compose down -v
Además borra los volúmenes del proyecto: se pierden los datos de la base de datos. Útil para empezar de cero, por ejemplo si cambiaste el usuario de Mongo y necesitás que se vuelva a crear.

Usar otro archivo

docker compose -f docker-compose-dev.yml up
-f elige un archivo que no se llama docker-compose.yml. Va antes del subcomando (up), porque es una opción de compose, no de up.
docker compose -f docker-compose-dev.yml down
Para bajar ese proyecto usá el mismo -f: sin él, Compose busca docker-compose.yml y no encuentra lo que levantaste.
docker compose -f docker-compose.yml -f docker-compose.override.yml up
Combina dos archivos: el primero es la base y el segundo agrega o reemplaza claves (por ejemplo, otro puerto o un volumen de código para desarrollo). Si existe un archivo llamado docker-compose.override.yml, docker compose up lo combina solo.
docker compose config
Muestra el YAML final tal como lo entiende Compose: con los archivos combinados y las variables de .env ya reemplazadas. Si el archivo tiene un error de sintaxis o de indentación, acá aparece el mensaje con la línea.

Operar servicios

docker compose ps
Lista los contenedores de este proyecto (solo los de esta carpeta), con su estado y puertos. running = corriendo; exited = se detuvo: mirá sus logs.
docker compose logs -f chanchito
Muestra los logs del servicio chanchito y sigue en vivo (-f). Sin nombre, muestra los de todos los servicios, con el nombre de cada uno al principio de la línea. Ctrl+C deja de mirar.
docker compose exec chanchito sh
Abre una terminal dentro del contenedor del servicio. Se usa el nombre del servicio del YAML (chanchito), no el del contenedor que crea Compose (carpeta-chanchito-1). Salís con exit.
docker compose restart chanchito
Detiene y vuelve a arrancar ese servicio, con la misma configuración. Ojo: si cambiaste el YAML o el código de una imagen, restart no lo aplica; para eso, up -d o up -d --build.
docker compose stop
docker compose start
stop detiene los contenedores del proyecto sin borrarlos y start los vuelve a arrancar tal como estaban. A diferencia de down, no se recrea nada.
docker compose build chanchito
Construye (o reconstruye) solo la imagen de ese servicio, sin arrancar nada. Después, docker compose up -d recrea el contenedor con la imagen nueva.
!

docker compose (con espacio) es la versión actual integrada en Docker. docker-compose (con guion) es la v1, ya discontinuada.

3

Claves del YAML

Lo que va dentro de cada servicio.

Cómo leer YAML. La sangría (espacios al principio de la línea) indica pertenencia: todo lo que está más a la derecha que chanchito: le pertenece a ese servicio. clave: valor es un dato; una línea que empieza con - es un elemento de una lista.

Usá siempre la misma cantidad de espacios (2 es lo habitual) y nunca tabs: un error de sangría cambia el significado o rompe el archivo.

services:            # nivel 0: sección
  chanchito:         # nivel 1: un servicio
    image: node:22   # nivel 2: dato del servicio
    ports:           # nivel 2: una lista...
      - "3000:3000"  # ...con un elemento

Referencia de claves

ClavePara quéEjemplo
servicesLos contenedores a crear (uno por clave)services: chanchito: …
buildConstruir desde un Dockerfile. Forma corta = carpeta; forma larga = context + dockerfilebuild: .
imageUsar una imagen ya hecha (Docker Hub)image: mongo:7
portsMapeo "HOST:CONTENEDOR" (entre comillas)- "3000:3000"

!

version: "3.9" al principio del archivo es obsoleto: Compose v2 lo ignora y muestra un warning. Podés borrarlo.

i

YAML usa espacios, nunca tabs. La indentación define la jerarquía; mantené siempre el mismo ancho (2 o 4 espacios).

4

Compose de producción

La imagen lleva el código adentro (Dockerfile con COPY).

Comentado

docker-compose.yml

docker-compose.ymldocker compose up
services:

  # Contenedor de nuestra aplicación
  chanchito:
    build: .              # busca el Dockerfile en la carpeta actual
    ports:
      - "3000:3000"       # PC:3000 -> contenedor:3000
    links:
      - monguito          # (legacy) chanchito habla con monguito

  # Contenedor de MongoDB
  monguito:
    image: mongo          # imagen oficial
    ports:
      - "27017:27017"
    environment:          # crea el usuario admin al iniciar
      - MONGO_INITDB_ROOT_USERNAME=mati
      - MONGO_INITDB_ROOT_PASSWORD=<password>
    volumes:
      - mongo-data:/data/db   # persiste los datos
      # mysql    -> /var/lib/mysql
      # postgres -> /var/lib/postgresql/data

# Declaración del volumen nombrado
volumes:
  mongo-data:
Mejorado

Versión recomendada

docker-compose.yml
services:
  chanchito:
    build: .
    ports:
      - "3000:3000"
    depends_on:
      - monguito          # arranca después de mongo
    environment:
      - MONGO_URL=mongodb://${MONGO_USER}:${MONGO_PASSWORD}@monguito:27017/miapp?authSource=admin
    restart: unless-stopped

  monguito:
    image: mongo:7        # versión fija
    ports:
      - "27017:27017"     # opcional: solo si querés entrar con Compass
    environment:
      - MONGO_INITDB_ROOT_USERNAME=${MONGO_USER}
      - MONGO_INITDB_ROOT_PASSWORD=${MONGO_PASSWORD}
    volumes:
      - mongo-data:/data/db

volumes:
  mongo-data:
  • depends_on en vez de links
  • Credenciales en .env, no en el YAML (no se suben a git)
  • En app.js: mongoose.connect(process.env.MONGO_URL)

Compose de desarrollo

Monta tu carpeta en el contenedor: editás y nodemon recarga, sin rebuild.

docker-compose-dev.yml

docker-compose-dev.yml-f docker-compose-dev.yml up
services:
  chanchito:
    build:
      context: .                  # carpeta usada como contexto
      dockerfile: Dockerfile.dev  # Dockerfile a usar
    ports:
      - "3000:3000"
    links:
      - monguito
    volumes:
      - .:/home/app               # reemplaza al COPY del Dockerfile

  monguito:
    image: mongo
    ports:
      - "27017:27017"
    environment:
      - MONGO_INITDB_ROOT_USERNAME=mati
      - MONGO_INITDB_ROOT_PASSWORD=<password>
    volumes:
      - mongo-data:/data/db

volumes:
  mongo-data:

Cómo funciona el bind mount

Antes: COPY . /home/app (copia fija en la imagen). Ahora: .:/home/app (carpeta compartida en vivo).

Variables y archivo .env

Saca contraseñas del YAML. Compose lee automáticamente el .env de la misma carpeta.

1. Crear .env

.envagregalo al .gitignore
MONGO_USER=mati
MONGO_PASSWORD=<password>

2. Usarlas en el compose

environment:
  - MONGO_INITDB_ROOT_USERNAME=${MONGO_USER}
  - MONGO_INITDB_ROOT_PASSWORD=${MONGO_PASSWORD}
# o pasar el archivo entero al contenedor:
env_file: .env

3. Verificar

docker compose config
Imprime el YAML con las variables del .env ya reemplazadas. Si ves un valor vacío donde esperabas la contraseña, el .env no está en la misma carpeta o la variable tiene otro nombre.
i

MONGO_INITDB_ROOT_* solo se aplica la primera vez (con el volumen vacío). Si cambiás la contraseña después, hacé down -v o cambiala dentro de Mongo.

Varios servicios: db · migrator · backend · frontend

El patrón de tu proyecto ASP.NET Core: el compose orquesta, cada Dockerfile solo construye.

Esqueleto

services:
  db:
    image: postgres:16
    environment:
      - POSTGRES_PASSWORD=${DB_PASSWORD}
    volumes:
      - pg-data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
      retries: 10

  migrator:
    build:
      context: ./aspnet-core          # TODA la solución
      dockerfile: src/<Proyecto>.DbMigrator/Dockerfile
    depends_on:
      db:
        condition: service_healthy    # espera a que la DB esté lista

  backend:
    build:
      context: ./aspnet-core
      dockerfile: src/<Proyecto>.HttpApi.Host/Dockerfile
    ports:
      - "44300:8080"                  # PC:44300 -> contenedor:8080
    environment:
      - ConnectionStrings__Default=Host=db;Database=app;Username=postgres;Password=${DB_PASSWORD}
    depends_on:
      migrator:
        condition: service_completed_successfully

  frontend:
    build: ./angular
    ports:
      - "4200:80"
    depends_on:
      - backend

volumes:
  pg-data:

Claves de este patrón

  • context = qué carpeta ve el Dockerfile. Si el proyecto depende de otros (Domain, Application…), el context tiene que ser la raíz de la solución.
  • dockerfile = ruta al Dockerfile relativa al context.
  • depends_on solo ordena el arranque. Para esperar a que algo esté listo usá condition: service_healthy + healthcheck.
  • service_completed_successfully: el backend arranca recién cuando el migrator terminó bien.
  • En .NET, __ (doble guion bajo) en una variable = : en appsettings.json (ConnectionStrings:Default).
  • El host de la DB en el connection string es el nombre del servicio (Host=db).
✓

Regla de oro: el Dockerfile no sabe de puertos externos, variables ni de otros contenedores. Todo eso vive en el compose.
